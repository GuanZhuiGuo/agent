# 案例 1：企业客服 Agent

> 用前面 8 个模块的方法论，完整设计一个企业客服 Agent。
> **这是最经典、成本收益最容易算清的 Agent 场景。**

---

## 背景

某 SaaS 公司，客服团队 20 人，日均工单 1500 单。
- 60% 工单是重复问题（怎么退费、怎么改密码、怎么升级版本…）
- 20% 涉及账户/订单查询
- 15% 需要客服操作（退款、开票、改套餐）
- 5% 复杂争议

**业务目标**：
- 把重复问题自动化率提到 70%
- 一线客服人力释放 30%
- 用户 CSAT 不下降

---

## 1. 能力光谱定位

- 从 "**Chatbot + RAG**" 起步
- 再演进到 "**工具调用 Agent**"（能查询账户、能自助改密）
- 不做"自主 Agent"（涉及钱的事必须人审）

🧭 选择 **工具调用 Agent + 工作流**。

---

## 2. 规划模式

- **主干是工作流**：分诊 → 识别意图 → 选子路径
- **子路径内部用 ReAct**：比如"账户查询"可能需要 2–3 次工具调用
- **敏感动作前加 HITL C 档**：退款必须人工确认

---

## 3. 记忆设计（填画布）

| 层 | 内容 |
|---|---|
| L1 工作 | 当前工单上下文 |
| L2 会话 | 本次对话历史 + 已查询结果 |
| L3 用户 | 用户 ID / 级别 / 偏好语言 / 历史工单摘要 |
| L4 任务 | 该工单的状态、已尝试方案 |
| L5 系统 | 通用客服话术库（可视为系统记忆或知识库） |

策略：
- 用户偏好语言、历史工单摘要 → 后台蒸馏进 L3
- 每次对话开场调 L3 + L4
- 用户手动补充的偏好立即写入
- 长期不用 90 天 TTL 过期

---

## 4. RAG 设计

| 项 | 选择 |
|---|---|
| 数据源 | 产品手册 / FAQ / 历史优质工单 / 政策文档 |
| 切分 | FAQ 按 Q-A 对；手册按 H2/H3 + 500 token |
| 元数据 | source, product_line, version, updated_at, lang, sensitive |
| 检索 | Hybrid（BM25 + 向量）+ Cohere Rerank |
| 过滤 | 按 product_line、lang 过滤 |
| 引用 | 强制引用；敏感（价格/法务）必须人审 |
| 兜底 | 召回为空 → 转人工 |

---

## 5. 工具清单

| 工具 | 类别 | HITL | 说明 |
|---|---|---|---|
| search_kb | Retrieval | A | 查知识库 |
| get_account_info | Read | A | 查当前用户账户状态 |
| get_orders | Read | A | 查订单（只能查本人） |
| reset_password_link | Write-可撤销 | B | 发送重置链接，用户点击才生效 |
| change_plan | Write | C | 改套餐 → 人审 |
| refund | Write | C | 退款 → 人审 |
| create_ticket | Write | B | 创建升级工单 |

⚠️ `refund` 有严格限额，超过 $100 强制转主管人审。

---

## 6. Multi-Agent？

**不需要。**

- 单 Agent + 工作流就能覆盖
- 上下文不会爆炸（单工单通常很短）
- 没有明显并行需求

**如果未来演进**：可能拆出一个"情绪安抚 / 投诉升级" sub-agent，用不同的 prompt 语气。但 V1 不做。

---

## 7. 栏杆

- 最大步数 / 工单：6
- 最大成本 / 工单：$0.05
- `refund` 工具最多 1 次
- 红线：不承诺折扣、不做法律建议、不讨论竞品

---

## 8. UX

- 展示 AI 身份 + 可随时"转人工"按钮
- 展示引用来源（"来自 FAQ / 账户问题"）
- 敏感动作（退款）显示"等待客服审核"状态
- 失败文案库：
  - 召回为空："资料里没找到直接答案，我帮你转接真人客服 →"
  - 工具失败："查询出了点问题，请稍后再试或 [转人工]"
  - 越权："这个操作需要账户主人操作，你可以 [发送申请邮件]"

---

## 9. 评估方案

- 黄金集：200 条（从历史工单抽样）
- Rubric：事实正确性、是否给引用、是否正确转人工、语气
- 红队：prompt injection、诱导越权退款、冒充用户
- LLM-as-Judge：用 Claude Sonnet 做批量评估
- 发布门槛：TSR ≥ 85%、红线 = 0、转人工成功率 ≥ 95%

---

## 10. 指标目标

| 指标 | 目标 | 说明 |
|---|---|---|
| 自动化解决率 | ≥ 70% | 无需人工介入完成 |
| CSAT | ≥ 4.3 | 不下降 |
| 平均响应时间 | ≤ 10s | |
| 转人工顺畅度 | ≥ 95% | 转接携带完整上下文 |
| 单工单成本 | ≤ $0.05 | |
| 误退款次数 | 0 | 红线 |

---

## 11. 成本估算

每工单平均：
- 3 步 LLM 调用，每步 2K in + 0.3K out
- Sonnet 级价格
- 成本 ≈ 3 × (2K × $3/M + 0.3K × $15/M) = $0.023 → **约 $0.05 上限内**

每月 1500 × 30 = 45000 工单
- 若 70% 自动化：≈ 31500 × $0.023 ≈ $725/月
- 对比 20 位客服的人力成本，ROI 极显著。

---

## 12. 上线节奏

1. W1–2：建黄金集、Prompt 基线
2. W3：Dogfood（内部客服模拟）
3. W4：Beta（100 个真实用户 opt-in）
4. W5：灰度 20%
5. W6：全量

---

## 13. 风险与应对

| 风险 | 应对 |
|---|---|
| 幻觉回答政策 | 强制引用 + 关键字段人审 |
| 退款被诱导 | 强 HITL + 金额红线 |
| 多语言用户体验差 | 先锁定中英，后续扩展 |
| 用户不信任 AI | 明显"转人工"入口 |

---

## 学到的事

1. **工作流 + 单 Agent** 是客服场景的最佳起点，不要上来就 Multi-Agent。
2. **HITL 档位要精细**：查账免审、改套餐人审、退款强人审。
3. **引用必须强制**：客服最容易因为"一句没来源的话"翻车。
4. **成本是天然可算的**：客服场景 ROI 很直观，立项时就把这笔账算给老板看。
