# 模块 01 · Agent 基础与 PM 视角

> 目标：把 Agent 的底层原理装进 PM 的"脑内 API"，以及——学会判断"不该做 Agent"的时刻。

---

## 1.1 Agent 到底在做什么：主循环拆解

每一个 Agent，不管外表多复杂，内核都是一个**循环**：

```
LOOP:
  1. 观察（Observe）   ← 用户输入 / 环境状态 / 工具返回
  2. 思考（Think）     ← LLM 基于上下文做推理
  3. 行动（Act）       ← 调工具 / 回复用户 / 更新记忆
  4. 判断是否结束     ← 没完继续 LOOP；完了 return
```

这被称作 **ReAct 循环**（Reason + Act）。

对 PM 来说，重要的不是"ReAct 是什么"，而是：

> **每一圈循环 = 一次 LLM 调用 = 一笔钱 + 一段延迟 + 一次可能出错**

所以你经常会听到工程讨论：
- "这个任务要 10 圈才能搞定" → 成本 × 10、延迟 × 10、错误率累积
- "能不能合并成 3 圈？" → 这是**产品设计问题**，不是只是工程问题

🧭 **PM 决策点**：你愿意为"更智能但更慢更贵"买单吗？你的用户愿意吗？

## 1.2 LLM 是"大脑"，但它有四个先天缺陷

PM 必须知道 LLM 的这四个"原厂毛病"，因为 Agent 的所有组件几乎都是在**补这些缺陷**：

| 缺陷 | 表现 | 补救组件 |
|---|---|---|
| **健忘** | 不记得上次聊了啥 | → 记忆（模块 02） |
| **不知道** | 没有你公司的私有知识 | → 知识库 / RAG（模块 03） |
| **不能做事** | 只能输出文本 | → 工具 / Action（模块 04） |
| **不会规划** | 复杂任务容易跑偏 | → 规划 / 工作流（模块 05） |

**这不是四个独立的模块，而是四个角度去"修"同一个大脑。**

可以这么理解：

```
Agent = LLM（大脑）
      + 记忆（让它记得）
      + 知识库（让它知道）
      + 工具（让它能做）
      + 规划（让它会做）
```

## 1.3 判断"该不该做成 Agent"的决策树

这是 PM 立项时**最重要**的一张图。

```
                ┌──────────────────────────────┐
                │ 用户的目标是什么？            │
                └──────────────┬───────────────┘
                               │
              ┌────────────────┼────────────────┐
              │                │                │
         只要答案         要答案+操作       要托付整件事
              │                │                │
              ▼                ▼                ▼
         ┌────────┐       ┌────────┐      ┌──────────────┐
         │ 用 RAG │       │ 用工作流│      │ 候选：Agent  │
         │ Chatbot│       │ + AI   │      └──────┬───────┘
         └────────┘       └────────┘             │
                                                  ▼
                              ┌───────────────────────────────┐
                              │ 步骤是否固定？                │
                              └────────────┬──────────────────┘
                                 是        │       否
                              ┌────────────┴─────────────┐
                              ▼                          ▼
                      固定流程 + AI（工作流）    Agent（动态规划）
```

**🧭 关键原则：能用工作流解决的，不要用自主 Agent。**

- 工作流：开发可控、成本可控、测试可做
- 自主 Agent：灵活但不可预测，评估难、成本高

这个原则被 Anthropic 在 *Building effective agents* 里反复强调。

---

## 1.4 Workflow vs. Agent：一张对比表

| 维度 | 工作流（Workflow） | 自主 Agent |
|---|---|---|
| 流程 | 人类预定义 | LLM 动态决定 |
| 可预测性 | 高 | 低 |
| 可测试性 | 好 | 难 |
| 成本 | 可控 | 波动大 |
| 适合场景 | 步骤相对稳定 | 长尾任务、未知任务 |
| 调试 | 像传统软件 | 要看 trace |
| 何时选 | 80% 的场景 | 真的需要灵活性的时候 |

**📌 PM 口诀**：**Workflow 是默认选项，Agent 是升级选项。**

## 1.5 上下文窗口：Agent 的"工作台面积"

一个常常被 PM 忽视但会直接决定设计的事实：

> **LLM 的上下文窗口（Context Window）= Agent 的工作台。**
> 桌子就这么大，能放的东西有限。

一次请求中上下文通常会被这样塞满：

```
[ System Prompt ]            ← 身份/能力/规则，基本不动
[ 工具说明       ]            ← 函数 schema + 描述
[ 记忆片段       ]            ← 跨会话
[ 知识库检索结果  ]            ← RAG 召回内容
[ 历史对话       ]            ← 本次会话
[ 用户最新输入   ]
```

一旦这些加起来逼近上限，就会：
- 截断（丢信息）
- 压缩（总结，容易失真）
- 检索（只选最相关的）

**🧭 PM 决策点**：在一个有限的"桌面"上，**哪些信息优先进来**？这就是模块 02（记忆）和模块 03（知识库）的核心命题。

⚠️ 常见错误：以为"上下文越大越好"。**实际上上下文越大：**
- 成本越高（按 token 计价）
- 延迟越大（模型推理变慢）
- 注意力越容易被干扰（"lost in the middle"）

## 1.6 PM 要掌握的六个基础词

做 Agent 评审时，你至少要能接住这几个词：

1. **Prompt / System Prompt** —— 给 Agent 的"岗位说明书"
2. **Context Window** —— 工作台大小
3. **Tool / Function Calling** —— 让 LLM 输出"我要调这个工具"的结构化指令
4. **Token** —— 计价单位；大致 1 汉字 ≈ 1–1.5 token
5. **Temperature** —— 创造性温度，越高越发散
6. **Trace** —— 一次任务的完整执行链路，是 Agent 的"黑匣子"

详见 [术语表](../glossary.md)。

## 1.7 PM 的"该不该做 Agent" Checklist

立项前，请**逐项**勾选。全勾 = 可以做；不全勾 = 考虑先做简化版。

- [ ] 用户有一个**具体可描述**的目标
- [ ] 用 Chatbot / RAG / 工作流**做不到**这个目标
- [ ] Agent 失败**不会**造成不可逆后果
- [ ] 我们可以清楚定义**"成功"**长什么样
- [ ] 我们有能力**评估**每个版本变好还是变差
- [ ] 业务**付得起**预估的单次任务成本
- [ ] 产品能接受 Agent 不是 100% 正确
- [ ] 有机制让用户**中止 / 纠正**错误行为

## 1.8 产品指标：Agent 版

早期 PM 常只看"满意度"。Agent 产品应关注更立体的指标：

### 📊 北极星指标（选一个）
- **任务完成率**（Task Success Rate, TSR）：端到端任务跑完且结果正确的比例

### 📊 效率指标
- 平均步数 / 任务
- 平均耗时 / 任务
- 平均成本 / 任务（$）

### 📊 质量指标
- 事实正确性（Factuality）
- 工具调用正确率
- 用户纠正率 / 中止率

### 📊 体验指标
- 首次响应时间（TTFT）
- 用户主动跳过 / 删除对话的比例

⚠️ 不要把"用户满意度"当唯一指标，Agent 很容易"听起来很自信但其实错了"，用户一开始感知不到。

## 1.9 案例速览

**案例**：某法律 SaaS 想做"AI 律师助手"。

- V0 方案：全自主 Agent，能自动起草合同、发邮件给对方、管理案件流程。
- V1 方案（推荐）：
  - 工作流 + AI：合同起草 = RAG + 填模板
  - 发邮件 → 必须人工确认
  - 案件流程 → 工作流

结果：V1 上线时间 -60%，准确率更高，律师更愿意用（**因为他们保留控制权**）。

**🎯 学到了**：先做**工作流 + AI**，把场景跑熟，再逐步把部分节点"Agent 化"。

## 1.10 练习

1. 选一个你正在做或见过的 AI 产品，用 **1.7 Checklist** 打分。
2. 用 **1.3 决策树**，找一个你项目中"不该做成自主 Agent 但做成了"的功能，说明应该退回哪一级。
3. 写下该产品的 **北极星指标**，并自评过去 2 周是否有量化数据。
