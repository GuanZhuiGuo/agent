# 模块 05 · 规划、推理与工作流

> 目标：掌握 Agent 怎么把"一个目标"拆成"一串动作"，PM 能在工作流 / ReAct / Plan-and-Execute / 反思等模式中做选型。

---

## 5.1 为什么规划是 Agent 的"骨架"

- 记忆（模块 02）= 血
- 知识（模块 03）= 肉
- 工具（模块 04）= 手脚
- **规划（本模块）= 骨架**

没有规划，多步任务会走成一团乱麻。

规划要回答三件事：
1. 目标怎么**拆**？
2. 步骤怎么**排**？
3. 遇到意外**怎么改**？

---

## 5.2 五种主流规划模式

从**规则强** → **自由度高**：

```
Workflow ─▶ Chain-of-Thought ─▶ ReAct ─▶ Plan-and-Execute ─▶ Reflection/Self-Critique
 ─────────────────────────────────────────────────────────────────────▶
  规则强                                                          自由度高
  可控性高                                                        复杂度高
```

### 5.2.1 Workflow（工作流）

- **人**把流程画出来（DAG）
- 每个节点可能调 LLM、调工具、人审
- LLM 在节点里**干具体活**，不负责"接下来去哪"

适合：步骤稳定的业务流程（报销、风控、合同审查）

### 5.2.2 Chain-of-Thought（CoT）

- 让 LLM 先"想一想"再回答
- 单次调用，没有工具循环
- 适合纯推理问题

### 5.2.3 ReAct（Reason + Act）

- 交替进行 "想 → 做 → 看结果 → 再想 → 再做"
- 是最主流的 Agent 循环模式
- 强在**边做边调整**

适合：工具多、路径不确定的任务

### 5.2.4 Plan-and-Execute

- 先**一次性**出一个完整计划（Plan）
- 再逐步执行（Execute）
- 出错时可以回到规划器重规划

适合：任务结构化、成本敏感（避免 ReAct 的回回问模型）

### 5.2.5 Reflection / Self-Critique

- Agent 执行完之后，**自己审视**结果，给自己找茬
- 不满意就迭代

适合：写作、代码、研究类任务；对质量比速度重要的场景

> **实际产品通常是组合使用**：
> "Plan-and-Execute 生成大骨架 → 每个节点里 ReAct 工具使用 → 整体结果做一次 Reflection"。

## 5.4 反思（Reflection）：低成本高收益的"产品杠杆"

**一句话：做完再看一眼。**

技术上：
- 让 Agent 在输出之前对自己的结果进行一次评估（按规则/rubric）
- 不合格 → 改一版

产品上你可以：
- 只对**关键节点**开反思（不是全程）
- 在"发出前"加一道（发邮件前先自检）
- 把反思结果**展示给用户**（"我检查了 3 件事"）→ 是信任来源

📊 经验数据：Reflection 可在写作/代码任务上让通过率提升 10–30%，代价是成本翻倍。

🧭 PM 决策点：在**哪一步**开反思，权衡质量 vs. 成本。

## 5.5 Guardrails：栏杆与红线

无论哪种规划，都要有"栏杆"：

| 栏杆类型 | 例子 |
|---|---|
| **步数上限** | 单任务最多 20 步 |
| **成本上限** | 单任务最多 $0.50 |
| **时间上限** | 超过 5 分钟必须中止 |
| **工具次数限制** | `send_email` 单任务最多 2 次 |
| **话题红线** | 不讨论竞品、不承诺折扣、不给医疗建议 |
| **人工 kill switch** | 用户可随时按"停止" |

⚠️ 缺少栏杆会出现两类事故：
- 成本爆炸（Agent 死循环烧钱）
- 话题越界（说了不该说的）

## 5.6 人机协作模式：四种典型形态

PM 要想清楚你的产品里，**谁是司机**：

```
A. Copilot（副驾）        人驾驶，Agent 建议
B. Pair（结对）           人 Agent 轮流操作
C. Review Gate（审阅关卡） Agent 做，人审
D. Autopilot（自动驾驶）  Agent 全程，人仅观察
```

🧭 PM 决策点：同一个产品，不同任务可能在不同模式下。

举例：GitHub Copilot / Cursor 的演进：
- Completions = A
- Chat = B
- Apply Edits = C
- Agent / Background Agents = D

**产品化路径建议：A → B → C → D，一阶一阶往上走**，每一级需要不同的信任与评估积累。

## 5.7 长任务 / 后台 Agent

当 Agent 要跑几分钟～几小时（比如深度研究、代码仓库重构），**同步对话 UI 彻底不适用**。要转变成：

- **任务化 UI**：像提交一个任务，而不是对话
- **进度可视化**：实时展示"Agent 现在在干嘛"
- **可中止 / 可追问**：用户能随时打断
- **异步通知**：完成后通过邮件 / IM 通知
- **Artifacts**：Agent 产出可下载、可复用的工件

典型例子：Manus、Devin、Claude Skills、ChatGPT Agent Tasks

这类产品，PM 要额外想清楚：
- 用户在等待期间怎么办？
- 失败怎么办？（重试？部分结果？）
- 多个任务并发怎么管理？

## 5.8 🛠 规划设计 Checklist

PM 写规划章节时至少回答：

- [ ] 选择了哪种规划模式？（工作流 / ReAct / Plan-Execute / 组合）
- [ ] 最大步数、最大成本、最大时间分别是多少？
- [ ] 哪些节点是必反思的？
- [ ] 哪些节点是必人审的？（接上模块 04 HITL）
- [ ] 失败了怎么兜底？
- [ ] 用户怎么看到"现在在干嘛"？
- [ ] 用户怎么中止 / 接管？
- [ ] 结果怎么交付（聊天 / 文件 / 工单）？

## 5.9 ⚠️ 反模式

1. **步数没有上限**：一旦卡住就烧钱。
2. **隐藏执行过程**：用户等 30 秒不知道发生什么。
3. **把工作流问题做成自主 Agent**：业务是稳定流程，却要 LLM 每一步自己决定下一步。
4. **把自主 Agent 问题做成工作流**：每次新需求都要改 DAG，研发累死。
5. **没有失败路径**：只设计了"happy path"。

---

## 5.10 📊 规划相关指标

| 指标 | 意义 |
|---|---|
| 任务完成率（TSR） | 北极星 |
| 平均步数 / 任务 | 规划效率 |
| 步数超限率 | 触达上限比例 |
| 反思触发后改进率 | 反思值不值得 |
| 用户接管率 | 人工 override 比例 |
| 中途放弃率 | 用户主动中止比例 |

## 5.11 案例速览

**案例**：一个"合同审查 Agent"。

**方案**：
- 整体用**工作流**（条款提取 → 风险扫描 → 交叉比对 → 生成报告）
- 每个节点内部用 **ReAct**（比如"风险扫描"里 Agent 可多次调规则库）
- 最后加一个 **Reflection**（用 rubric 自查报告结构）
- 最终交付前加 **人审关卡（C 档）**

**结果**：
- 可控性 / 成本可控（因为主干是工作流）
- 单节点灵活（因为内部是 Agent）
- 质量保障（因为有 Reflection + 人审）

## 5.12 练习

1. 为你要做的 Agent 任务，画一个**规划模式图**（可以手绘拍照）。
2. 列出你的"栏杆"配置表：最大步数 / 成本 / 时间 / 工具次数 / 话题红线。
3. 定义一张"进度可视化"方案：用户在等待时能看到什么？
4. 对照 5.9 反模式自检，记录踩中的项与改进方向。
