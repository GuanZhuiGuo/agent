# 模块 04 · 工具与 Action 设计

> 目标：从"能说话的 AI"跨到"能做事的 AI"。PM 要学会设计工具清单、权限矩阵和人类在环（HITL）策略。

---

## 4.1 没有工具，就没有 Agent

> **Chatbot：输出文字。Agent：输出行动。**
> 而"行动"的载体就是**工具（Tools）**。

一个 Agent 能不能帮用户报销、下单、改代码、发邮件，**完全取决于它挂了哪些工具**。所以工具清单 = Agent 的**能力边界**。

这是 PM 定义产品的最直接的抓手。

---

## 4.2 Tool / Function Calling 是怎么工作的

PM 不用懂实现，但要理解这个动作流程：

```
 用户："帮我查下上个月的销售额"
      │
      ▼
 LLM 看到工具清单里有 query_sales(month) 这个函数
      │
      ▼
 LLM 输出一个结构化指令：
 { "tool": "query_sales", "args": { "month": "2026-04" } }
      │
      ▼
 运行时（Agent 框架）解析指令 → 真正调用这个工具 → 拿到结果
      │
      ▼
 结果塞回 LLM 的上下文 → LLM 基于结果给出自然语言回答
```

**重点**：LLM 本身不"调用工具"，它只是**输出一段"我要调哪个工具、参数是啥"的意图**。真正执行的是外部代码（Runtime）。

🧭 对 PM 的意义：
- 工具的**名字 + 描述 + 参数 schema** 就是给 LLM 的"使用说明书"，这是 PM 要打磨的**文案**。
- 工具能做多少事，等于你给它的 schema 有多细。

---

## 4.3 工具的五种典型类别

| 类别 | 例子 | 代价 |
|---|---|---|
| **Retrieval 检索类** | 搜索知识库、查数据库 | 低风险，主要算成本 |
| **Computation 计算类** | 执行代码、算表格、计算器 | 中等（沙箱要做好） |
| **Read API 只读接口** | 查 CRM、查订单、查日程 | 数据合规、频次控制 |
| **Write API 写操作** | 发邮件、下单、改记录、打款 | 高风险，必须审批/兜底 |
| **UI 操作类** | 浏览器自动化、桌面控制 | 最高风险，操作不可复现 |

🧭 **PM 决策点**：你真的需要让 Agent 做到"哪一层"？

一个非常实用的原则：

> **只读易做，写入慎做，不可逆绝不自动。**

---

## 4.4 工具粒度：粗 or 细？

一个典型讨论：要一个 `send_email(to, subject, body)` 大工具，还是拆成 `compose_draft / review_draft / send`？

| 粒度 | 优点 | 缺点 |
|---|---|---|
| 粗粒度 | LLM 少做决策、步数少 | 灵活性差、难兜底 |
| 细粒度 | 组合自由、可插入审批 | 步数多、成本高 |

**实践**：
- 高风险动作拆细（可在中间加审批节点）
- 低风险动作可粗（减少步数）

⚠️ 工具过多（>30 个）会让 LLM "选困难"，命中率下降。解决：**工具分组 / 动态加载**（按场景加载子集）。

## 4.5 工具描述就是 Prompt（PM 亲自写）

每个工具需要 4 件事：

```
name:        query_sales
description: 查询某月的销售额。适用于用户问"销量/销售/GMV"等。
             ⚠️ 注意：返回按自然月聚合，不支持跨月。
parameters:
  - month:   必填，格式 YYYY-MM
  - region:  可选，默认全国
returns:     { total, by_category }
```

**PM 亲自写 description 的原因**：
- 这是 LLM **选工具**的决策依据
- 写得含糊 → Agent 乱选、要么不选要么选错
- 写得精准 + 举正反例 → 正确率直接上一个台阶

💡 Tips：
- description 里明确"**什么情况用、什么情况不用**"
- 参数要写清**格式约束**（日期格式、枚举值）
- 可以塞一两句"**如果用户只说'上个月'，请自行换算成 YYYY-MM**"

## 4.6 Tool Use 的 4 种失败模式

Agent 用工具翻车，基本逃不过这 4 种：

### 4.6.1 选错工具
有 10 个工具，LLM 调了一个不相关的。
对策：分组、限制、在 description 里强调边界。

### 4.6.2 参数错
日期格式错了、ID 少了一位、region 写了中文。
对策：schema 严格校验 + 运行时友好错误反馈给 LLM（让它自我纠正）。

### 4.6.3 循环调用
Agent 陷入"调一次 → 不满意 → 再调一次 → …"的死循环。
对策：**最大步数上限**、**最大成本上限**、**自检环节**、**失败兜底**。

### 4.6.4 调用成功但用错了结果
工具返回一大段 JSON，LLM 只看了一半就答了。
对策：**工具结果后处理**（摘要、结构化），不要把原始长结果全丢给 LLM。

## 4.8 Human-in-the-loop（HITL）：人类在环

PM 必须明确定义**哪些动作需要人工确认**。三档机制：

```
┌──────────────────────────────────────────────┐
│ A 档：全自动执行                              │
│   低风险、可逆、频次高                        │
│   例：查资料、生成草稿                        │
├──────────────────────────────────────────────┤
│ B 档：事后可撤销                              │
│   中等风险，但可回滚/撤回                     │
│   例：创建草稿、保存文件                      │
├──────────────────────────────────────────────┤
│ C 档：事前人工确认                            │
│   高风险、不可逆                              │
│   例：发邮件、下单、打款、删库                │
└──────────────────────────────────────────────┘
```

🧭 PM 决策点：给每一个工具划定档位，写进 PRD。

⚠️ 很多产品失败的原因是 **C 档也自动执行了**——一次错误邮件发出去就回不来了。

---

## 4.9 错误处理：Agent 如何"吃下"工具错误

一个成熟 Agent 遇到工具报错不该直接崩，应该：

```
工具报错
  ├── 是参数错 → LLM 读错误消息，修正重试（最多 N 次）
  ├── 是权限错 → 转向用户："请先授权 X"
  ├── 是暂时性错（503）→ 退避重试
  └── 是永久性错（不存在）→ 换方案 / 告知用户 / 转人工
```

PM 要定义：
- 每种错误的**用户可见文案**
- 最大重试次数
- 超过后的**兜底流程**

## 4.10 📊 工具相关的指标

| 指标 | 意义 |
|---|---|
| 工具调用成功率 | 每个工具分别统计 |
| 工具调用分布 | 哪个工具被滥用 / 没被用 |
| 参数错误率 | 说明 description 或 schema 要打磨 |
| 平均每任务工具调用数 | 太多说明规划差 |
| HITL 通过率 | 人工否决越多 → Agent 越不被信任 |
| 高风险动作错误次数 | 必须接近 0 |

## 4.11 一个真实反例

**场景**：一家公司做"财务报销 Agent"，想让它自动把发票上传到系统并提交审批。

**V0 设计**：一个大工具 `submit_expense(receipt_image)`，内部完成 OCR + 字段填写 + 提交。
**结果**：
- OCR 错字段，Agent 不知道
- 提交后发现部门代码错，不能撤销
- 财务部投诉：这比人工还慢

**V1 改造**：
- 拆成 `ocr_receipt / fill_form / preview / submit`
- `preview` 是人必看的一步（HITL C 档）
- `submit` 按下才提交，提交前可编辑

**效果**：错误率降 85%，用户信任回来。

🎯 **学到**：不是"能做"就"要自动做"。**做到哪一步前停下，让人按一下**，是产品力。

## 4.12 练习

1. 为你的 Agent 产品列出**工具清单**（按 4.7 模板）。
2. 对每个工具分配 HITL 档位（A / B / C），给出理由。
3. 给 3 个高频工具各写一段**高质量 description**（至少包含"什么情况用、什么情况不用、参数格式、易错点"）。
4. 写一段"工具调用失败"的**用户可见文案**，要求：不暴露技术细节、给出下一步建议。
