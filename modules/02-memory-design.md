# 模块 02 · Agent 记忆设计 ⭐

> 目标：理解 Agent 的多层记忆架构，掌握 PM 在记忆上要做的核心决策，能独立产出一份"记忆画布"。

**本模块是整门课最容易产生差异化产品体验的一章。**

---

## 2.1 为什么记忆是 PM 必须亲自管的事

用户抱怨 Agent 的前三名，几乎永远有一条是：

> "我上次就告诉过它了。"

记忆决定了：
- **产品粘性**：记得越多，用户越不愿意换
- **个性化体验**：Agent 懂"我是谁"
- **效率**：不需要反复解释上下文
- **合规风险**：记得太多 = 隐私炸弹

**记忆不是工程问题，是产品问题。** 因为：
- 记什么 = 你定义产品边界
- 存多久 = 你定义用户信任边界
- 谁能看到 / 改动 = 你定义产品的合规形态

---

## 2.2 Agent 的五层记忆模型

把 "记忆" 当成一个词是 PM 最容易踩的坑。一个成熟 Agent 至少有这 5 层：

```
┌─────────────────────────────────────────────────────────────────┐
│  时间/持久度 ▶                                                   │
├─────────────────────────────────────────────────────────────────┤
│                                                                  │
│  L1 工作记忆     单次 LLM 调用内的上下文       几秒              │
│     (Working)    System prompt + 对话历史                        │
│                                                                  │
│  L2 会话记忆     单次对话 Session 内的状态     几分-几小时       │
│     (Session)    对话历史 + 已调工具 + 草稿                      │
│                                                                  │
│  L3 用户记忆     跨会话的用户个性化信息        月-年             │
│     (User)       偏好 / 身份 / 习惯 / 历史任务                    │
│                                                                  │
│  L4 任务记忆     特定任务实例的长期状态        项目周期          │
│     (Task)       一个 CRM 案子、一份长文档的进度                  │
│                                                                  │
│  L5 系统记忆     Agent 自己学到的经验/技能      持续              │
│     (Semantic)   从过往所有交互中蒸馏出的通用知识                 │
│                                                                  │
└─────────────────────────────────────────────────────────────────┘
```

### 对应到经典认知心理学分类

| 层级 | 类型 | 心理学对应 | 例子 |
|---|---|---|---|
| L1 | 短期 | 工作记忆 | "我刚才说的那段代码" |
| L2 | 短期 | 工作记忆 | "本次对话里我们已经讨论过的方案" |
| L3 | 长期 - 情景式 | Episodic | "用户喜欢 Python，不爱写注释" |
| L4 | 长期 - 情景式 | Episodic | "这个项目目前卡在数据对齐" |
| L5 | 长期 - 语义式 | Semantic | "处理 X 类问题的最佳实践" |

还有一种特殊的：
- **过程性记忆（Procedural）**：Agent"怎么做"的 know-how（通常以 System Prompt 或工作流 DSL 形式存在，算是开发者一侧的记忆）

---

## 2.3 一张表看清各层该记什么

| 层 | 存什么 | 存在哪里 | 谁能读 | 谁能写 |
|---|---|---|---|---|
| L1 工作 | 当前 prompt + 历史对话 | 上下文窗口 | 当前调用 | 自动 |
| L2 会话 | 本次 session 所有消息/工具/草稿 | 内存 / Redis | 当前用户当前 session | 自动 + 用户 |
| L3 用户 | 偏好、画像、长期习惯 | 结构化 DB + 向量库 | 当前用户 | Agent + 用户手动 |
| L4 任务 | 项目状态、里程碑、上下文 | 文档 / 数据库 | 被授权的人 | Agent + 协作者 |
| L5 系统 | Agent 通用经验 | 知识库 | 所有用户（可能） | 工程 / 自动蒸馏 |

**🧭 PM 决策点**：
1. 产品里**每一条信息**属于哪一层？（决定存储形态）
2. 用户**能否查看 / 编辑 / 删除**每一层？（决定合规形态）
3. 哪些信息**跨用户共享**？（L5 是否共享？商业机密？）

## 2.4 记忆的四个核心动作

工程实现千变万化，但 PM 只需理解四个动作：

```
  ┌─────────┐       ┌─────────┐       ┌─────────┐       ┌─────────┐
  │  Write  │  ──▶  │ Retrieve│  ──▶  │  Update │  ──▶  │  Forget │
  │  写入    │       │  检索    │       │  更新    │       │  遗忘    │
  └─────────┘       └─────────┘       └─────────┘       └─────────┘
    什么时候记      什么时候拿出来       冲突怎么办          什么时候忘
```

### 2.4.1 Write：什么时候记？

三种主流策略：

| 策略 | 做法 | 优 | 劣 |
|---|---|---|---|
| **Hot Path（热路径）** | 对话中即时写入 | 实时 | 增加延迟、成本 |
| **Background（后台）** | 会话结束后异步蒸馏 | 不拖慢用户 | 有延迟 |
| **User-Initiated** | 用户说"记住这个" | 可控、可解释 | 依赖用户行为 |

ChatGPT / Claude 的 Memory 功能基本是 **Background + User-Initiated 组合**。

🧭 **PM 决策点**：选哪种策略，取决于你对实时性 vs. 成本的偏好。

### 2.4.2 Retrieve：怎么找出来？

三种主要方式：

- **键值**：`user_id → profile`（最快，适合结构化）
- **向量语义检索**：按相似度召回相关记忆（适合非结构化经验）
- **时间衰减**：最近的优先（适合会话层）

实际产品一般是**混合检索**：先按用户 ID 过滤，再在用户的记忆池里向量召回 Top-K。

### 2.4.3 Update：冲突怎么处理？

真实例子：
- 用户 3 月说"我喜欢 Python"
- 用户 8 月说"最近在做 Rust 项目"
- Agent 应该记什么？

常见策略：
- **覆盖（Overwrite）**：用新的替换旧的 —— 简单但会丢上下文
- **追加（Append）**：都留着，加时间戳 —— 不丢信息但容易矛盾
- **蒸馏（Distill）**：合并成新描述 "Python 为主，最近在学 Rust" —— 效果好但贵

**🧭 PM 决策点**：用户改一次偏好要不要问他"这是临时的还是永久的？"

### 2.4.4 Forget：记忆的"反功能"

这是最容易被忽视、但最重要的一步。

为什么要遗忘：
- 记忆越多 → 检索越慢 / 越噪
- 记忆越多 → 成本越高
- 过时记忆 → 事实错误
- 隐私合规 → 必须支持删除（GDPR / 国内个人信息保护法）

遗忘的方式：
- **TTL**（过期时间）
- **重要性打分**，低分淘汰
- **用户主动删除**
- **定期蒸馏 + 清旧**

⚠️ PM 必须在产品里**暴露"管理我的记忆"入口**。这是合规底线，也是用户信任支点。

## 2.5 主流记忆架构实例

### 2.5.1 ChatGPT / Claude 风格：用户级长期记忆

- **写入**：后台蒸馏 + 用户主动标注
- **存储**：结构化 JSON 条目（"用户是 PM、喜欢简洁"）
- **检索**：每轮对话塞进 system prompt
- **治理**：Settings 里可查看/删除单条

**优点**：透明、可控
**缺点**：所有记忆硬塞上下文会占用 token

### 2.5.2 MemGPT / 分层记忆（Letta）

- 把记忆当成**操作系统的内存管理**
- LLM 可以**自己决定**把信息从"热记忆"换到"冷存储"（类似内存-磁盘分页）
- 给 Agent 工具：`save_core_memory` / `search_archival_memory`

**适合**：需要 Agent 自主管理大量记忆的场景

### 2.5.3 多用户协作型：项目/空间级记忆

- 像 Notion AI、Linear 这类
- **主体**是项目/工作区，而不是单个用户
- **权限**更复杂：谁能读这条任务记忆？
- 经常和**知识库**难以切分（见模块 03）

### 2.5.4 Agent 自我反思型（Reflexion / ReAct + Memory）

- 每次任务结束，Agent 写一段 "我学到了什么"
- 下次类似任务时检索这些反思
- 适合编程 Agent、研究 Agent

## 2.7 ⚠️ 常见反模式

### 反模式 1：把"所有历史消息都塞进上下文"当记忆
现象：早期做法，消息一多就爆炸。
后果：成本 × N、延迟 × N、质量下降（lost in the middle）。
对策：引入 L2 摘要 + L3 用户记忆。

### 反模式 2：把记忆和知识库混为一谈
现象：把 FAQ 和"用户偏好"放在同一个向量库里。
后果：检索相互干扰，权限混乱。
对策：L3/L4 是记忆；静态文档是知识库（模块 03）。

### 反模式 3：Agent 自主决定记什么，但用户不知情
后果：合规风险 + 信任危机。
对策：用户必须能**看到 + 编辑 + 删除**。

### 反模式 4：永远只追加不清理
后果：记忆越多越乱，老信息拖累新判断。
对策：必须有遗忘策略。

### 反模式 5：记忆只给 Agent 看，不给用户看
后果：失去了"陪伴感"和品牌资产。
对策：让记忆**可视化**，这是一个强体验点（比如年终报告）。

## 2.8 📊 记忆相关的指标

上线后你应该看这些：

| 指标 | 口径 | 意义 |
|---|---|---|
| 记忆召回命中率 | 有相关记忆且被召回 / 总需要 | 记忆是否真的"帮到" |
| 记忆误召回率 | 召回了但不相关 / 召回总数 | 记忆是否"帮倒忙" |
| 用户主动添加记忆次数 | 用户显式要求"记住" | 信任度代理指标 |
| 用户删除记忆次数 | 删除数 / 总记忆数 | 质量 / 侵犯感指标 |
| 平均上下文 token 中记忆占比 | 记忆 token / 总上下文 | 成本结构透视 |

## 2.9 案例：给编程 Agent 设计记忆

**场景**：类 Cursor 的编程助手 Agent。

| 层 | 存什么 | 为什么 |
|---|---|---|
| L1 工作 | 当前打开的文件片段、当前 task | 当下任务必需 |
| L2 会话 | 本次对话尝试过的方案、已失败的 patch | 不再重复踩坑 |
| L3 用户 | 代码风格（双引号 vs 单引号、tab vs space）、常用库 | 跨项目一致性 |
| L4 项目 | 该仓库的架构说明、模块职责、README 摘要 | 项目专属上下文 |
| L5 系统 | "修复类型错误的通用步骤"这种通用技能 | 全用户共享 |

🎯 这种分层让它"**像队友**"而不是"**像搜索引擎**"。

## 2.10 练习

1. 拿你正在做的（或想做的）Agent 产品，填一遍 **2.6 记忆画布**。
2. 针对 **2.7 五个反模式**，检查你的产品是否触犯了哪一个，给出整改方案。
3. 为你的产品设计 **3 个记忆相关指标**，并说出每个指标"高 / 低"分别代表什么问题。
4. 写一段文案：向用户解释"我们记了什么、你能怎么控制"（这是合规文案，PM 要自己能写出来）。
