# 模块 03 · 知识库与 RAG 设计 ⭐

> 目标：搞懂 RAG 的每一环在做什么取舍，能与研发就"为什么答得不准"进行有效对话，产出一份 RAG 设计文档。

---

## 3.1 为什么 PM 必须懂 RAG

"知识库答得不准"是 Agent 产品最常见的差评之一。每一次差评背后，几乎都不是"模型不行"，而是 **RAG 管道里某一环没调好**。

而这条管道的每一环，几乎都需要 PM 做**业务判断**：
- 什么内容要入库？
- 文档按什么粒度切？
- 检索到多少条够？
- 多个来源冲突时信谁？
- 答不出时怎么办？

不懂 RAG，你只能喊"再优化一下"。懂了 RAG，你可以定位到**具体环节**。

## 3.3 离线管道：建库的 5 个决策点

### 3.3.1 数据源 Data Source

🧭 决策：
- **哪些内容入库？** 不是越多越好。**噪声**会拖垮 RAG。
- **入库频率？** 每天 / 每小时 / 实时？
- **权限模型？** 多租户如何隔离？同一问答里哪些文档"A 用户能看、B 用户不能"？

⚠️ 陷阱：把整个 Wiki 全部入库当作 V1。**90% 的过时、冗余、重复文档，会让 Agent 越读越糊涂。**

### 3.3.2 清洗 Cleaning

PDF 转文本、表格提取、去页眉页脚、OCR、Markdown 结构保留……

PM 不用管技术实现，但要在 PRD 里写清**每种源文档的处理预期**：

| 源类型 | 处理期望 |
|---|---|
| Word / Google Docs | 保留标题层级、列表、表格 |
| PDF | OCR 质量 > 95%；表格结构不能丢 |
| 网页 | 去导航、去广告、保留正文 |
| Excel | 按行构造上下文、保留表头 |
| 代码仓库 | 按文件/函数分块 |

### 3.3.3 切分 Chunking

**最容易拉开差距的一环。** 切不好，后面怎么调都救不回来。

主流切法：

| 方法 | 做法 | 适合 |
|---|---|---|
| 固定长度 | 每 N token 一块 | 通用 baseline |
| 按标题层级 | H1/H2/H3 自然切 | 结构化文档 |
| 语义切分 | 按语义边界切 | 叙述性长文 |
| 父子分块 | 小 chunk 检索，回大 chunk 给 LLM | 高精召回+充分上下文 |
| 代码切分 | 按函数/类切 | 代码库 |

🧭 **PM 决策点**：
- 切太小 → 丢上下文 → 答得片面
- 切太大 → 召回噪音多 → 答得跑偏
- 一般起步：**300–800 tokens + 10–15% overlap**，然后根据评估调

⚠️ 陷阱：**表格、列表、代码段被从中间切断**，是 RAG 翻车的高频原因。

### 3.3.4 元数据 Metadata

每个 chunk 除了内容，必须带这些"标签"：

```json
{
  "content": "...",
  "source": "产品手册 v3.2",
  "section": "第 5 章 / 退货流程",
  "updated_at": "2026-03-15",
  "tenant_id": "customer-42",
  "permission_tags": ["public"],
  "lang": "zh",
  "version": "3.2"
}
```

**元数据决定了你能做哪些"过滤"**：
- 只查当前租户的
- 只查最近 6 个月的
- 只查公开权限的
- 只查中文的

🧭 PM 决策点：哪些**过滤维度**是业务必需的？在 V1 就要想清楚，后补改代价高。

### 3.3.5 向量化 Embedding

PM 要知道：
- **不同语言不同 embedding 模型表现差异大**，中文场景请选中文优化模型
- **embedding 模型一换，全库要重建**，所以早期选型要慎重
- **维度越高不等于越好**，但太低会损失语义

## 3.4 在线管道：查询的 5 个关键环节

### 3.4.1 Query Understanding / Rewriting

用户问题往往：
- 不完整（"那个怎么办？"）
- 有口语（"嗯那个东西…"）
- 指代历史上下文（"上次你说的方案"）
- 一句话里有多个问题

**处理方式**：
- **改写**：结合对话历史补全为完整问题
- **分解**：一句多问 → 多个子问题
- **扩展**：加同义词、相关术语（HyDE 等）

🧭 PM 决策点：要不要让用户**看到**改写后的查询？看到能纠正，不看到更流畅。

### 3.4.2 Retrieval 检索

三大检索方式，真正好用的系统都是**混合（Hybrid）**：

| 方式 | 强项 | 弱项 |
|---|---|---|
| 向量语义检索 | 同义表达、语义相近 | 精确术语、数字、代码 |
| 关键词检索（BM25） | 专有名词、代码、ID | 同义转述 |
| 结构化过滤 | 元数据筛选 | 不"理解"内容 |

**Hybrid 检索**：先用 BM25 + 向量检索各召回 Top-K，合并再去重。

### 3.4.3 Rerank 重排

召回阶段通常"宽"召回（K=20–50），然后用一个**更贵更准**的模型从里面挑真正相关的 Top-3~5 给 LLM。

**为什么需要**：向量检索的相关度分数 ≠ 真的有用。Rerank 模型专门判断"这段内容**对回答这个问题**有没有帮助"。

📊 影响显著：Rerank 一般能让答案正确率提升 10–30%。

### 3.4.4 生成 Generation

Prompt 里通常长这样：

```
你是 xxx 助手，回答问题时：
- 只使用【参考资料】里的信息
- 每条结论后用 [1][2] 标注来源
- 如果参考资料里没有，明确告诉用户"资料中未提及"

【参考资料】
[1] （来自 产品手册 v3.2 / 第 5 章）
...
[2] （来自 FAQ / 2026-03）
...

【用户问题】
用户：xxxxx
```

🧭 PM 决策点：
- 要不要**强制引用**？（严肃场景要，闲聊场景不必）
- 引用**颗粒度**：段落级 / 句子级？
- 没查到时 Agent 怎么说？（不要编！）

### 3.4.5 兜底与降级

答不出来的时候，比硬答要好的是**优雅降级**：

- "这个问题我不确定，建议联系客服"
- "资料里没有直接答案，但我找到了这些可能相关的文档"
- "你是指 X 还是 Y？"（反问消歧）

⚠️ **产品原则**：**Agent 可以说"不知道"，但不能说错。说错比说不知道代价大 10 倍。**

## 3.5 RAG vs. 记忆：两个最容易混淆的东西

| 维度 | 知识库（RAG） | 记忆（Memory） |
|---|---|---|
| 内容 | 静态 / 准静态文档 | 动态 / 交互产生 |
| 主体 | 通常和用户无关 | 属于某个用户 / 项目 |
| 写入 | 工程同步 / 文档编辑 | 交互中产生或蒸馏 |
| 更新 | 有版本有审核 | 高频、零散 |
| 权限 | 租户 / 部门 | 用户 / 项目 |
| 示例 | 公司 Wiki、产品手册 | "用户喜欢 Python" |

**口诀**：**知识库是教材，记忆是笔记。**

对 PM：
- 如果内容是"大家都看同一份"的 → **知识库**
- 如果内容是"每人一份、每人不同"的 → **记忆**
- 同一条信息可能两边都要一份（比如"公司退货政策" vs. "某客户和我们谈过的特殊退货条款"）

## 3.6 RAG 的 Agent 化：Agentic RAG

传统 RAG 是"查一次 → 答"。Agentic RAG 让 Agent **多次、自主**地查：

```
用户问 → Agent 评估
          ├── 信息够？    → 直接答
          ├── 需要再查？  → 改写 query 再检索
          ├── 需要多个源？→ 并行多检索
          └── 需要推理？  → 分解子问题 + 串行检索
```

适合：
- 开放性问题（"帮我调研竞品定价策略"）
- 需要综合多文档的问题

不适合：
- 简单 FAQ（一次检索够用，多查浪费）

🧭 PM 决策点：**什么样的问题升级到 Agentic RAG**？要设置**复杂度路由**，不是所有问题都值得多轮。

## 3.7 🛠 RAG 设计文档模板

PM 写 RAG PRD 请至少回答：

```
1. 知识覆盖范围
   - 包含：[  ]
   - 不包含：[  ]

2. 文档源清单
   - 源 / 格式 / 更新方式 / 责任人 / 权限

3. 切分策略
   - 起步方案：chunk size / overlap / 切法

4. 元数据字段
   - 必备字段（租户、时间、版本…）

5. 检索策略
   - 召回方式：向量 / BM25 / Hybrid
   - Top-K 起步值
   - 是否 Rerank

6. 生成策略
   - System Prompt 基调
   - 是否强制引用
   - "不知道" 的兜底话术

7. 降级与失败
   - 召回为空 → ?
   - 文档冲突 → ?
   - 权限拒绝 → ?

8. 评估
   - 黄金问答集规模
   - 指标（见 3.9）
   - 多久评一次

9. 运营
   - 差评 → 问题归因 → 流程谁跟进
```

---

## 3.8 ⚠️ 常见反模式

1. **把所有文档一股脑入库**：信噪比低 → 先选精。
2. **只用向量检索**：精确术语查不中 → Hybrid。
3. **没有 Rerank**：召回不等于好答案。
4. **不带元数据**：没法做权限、时间、版本过滤。
5. **不管文档更新**：老政策继续答 → 必须有版本化与 TTL。
6. **没有"我不知道"策略**：硬答 = 幻觉 = 信任崩塌。
7. **没有评估集**：每次优化靠感觉。
8. **把记忆和知识库混用**：权限和更新机制完全不同，会互相拖累。

## 3.9 📊 RAG 指标体系

### 检索侧

| 指标 | 口径 | 工具 |
|---|---|---|
| Recall@K | 正确答案所在 chunk 是否在 Top-K 内 | 黄金集评测 |
| MRR | 正确答案在 Top-K 中的平均倒数排名 | 黄金集评测 |
| Hit Rate | 有相关 chunk 被召回的查询比例 | 同上 |

### 生成侧

| 指标 | 口径 | 工具 |
|---|---|---|
| Faithfulness / Groundedness | 答案有多少部分有参考资料支撑 | LLM-as-judge / 人工 |
| Answer Relevance | 答案有多相关 | LLM-as-judge |
| Context Relevance | 召回的 context 有多相关 | LLM-as-judge |

### 业务侧

| 指标 | 口径 |
|---|---|
| 回答可用率 | 用户标记"有用"比例 |
| 人工介入率 | 用户转人工的比例 |
| 差评归因分布 | 检索错 / 切分错 / 生成错 的占比 |

## 3.10 案例：企业客服知识库 Agent

**数据源**：
- 产品手册 PDF
- 历史工单 Q&A
- 官网 FAQ
- 政策文档

**切分**：
- 手册按 H2/H3 + 500 token；FAQ 按问答对；工单保留 Q+A 为一对。

**元数据**：
- `source`, `product_line`, `version`, `updated_at`, `lang`, `sensitive_flag`

**检索**：
- Hybrid（BM25 + 向量）+ Cohere Rerank + 按 product_line 过滤

**生成**：
- 强制每条结论附引用；"资料未提及"时给出转人工入口。

**降级**：
- 召回为空 → 直接转人工
- 答案涉及敏感（价格/法务）→ 强制人审

**评估**：
- 500 条黄金问答集每周评估
- 业务侧"5 星率 ≥ 4.3" 为发布门槛

## 3.11 练习

1. 为你所在产品写一份 RAG 设计文档（按 3.7 模板）。
2. 挑 10 条"答得不准"的真实问答，分别归因到 3.2 管道的哪一环。
3. 为产品设计 5 条"降级话术"，覆盖不同失败场景。
4. 写一条给用户的"知识时效"说明：我们的资料截至什么时候？
