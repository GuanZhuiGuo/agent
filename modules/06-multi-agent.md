# 模块 06 · Multi-Agent 系统设计 ⭐

> 目标：搞清楚"什么时候该拆成多 Agent、怎么拆、拆完怎么协作、怎么治理"。这是 2024–2026 行业讨论最激烈的话题。

---

## 6.1 先泼一盆冷水：Multi-Agent 不是"越多越好"

一个反常识的事实：

> **很多你以为需要多个 Agent 的场景，一个设计良好的单 Agent 就够了。**

Anthropic 的 *Building effective agents* 反复提醒：**能用工作流 + 单 Agent 解决的，不要拆成多 Agent。**

为什么人们过早上 Multi-Agent：
- 看到"团队协作"的隐喻很吸引人
- 框架鼓励这样做（AutoGen / CrewAI / MetaGPT 有示范）
- 觉得拆得细工程更清晰

真实后果：
- **延迟**变成 N 倍
- **成本**变成 N 倍
- **错误传播**：一个环节错，下游全错
- **协调 Prompt** 的维护成本很高

🧭 **PM 决策原则：**
> **拆成多 Agent 的收益，必须大于增加的成本与复杂度。**

---

## 6.2 什么时候真的需要 Multi-Agent

以下至少一条成立，才考虑：

1. **角色/专长差异巨大**：不同 Agent 需要不同 prompt、工具、甚至不同模型。
2. **并行加速**：多个子任务可以同时推进（研究型最典型）。
3. **上下文隔离**：每个 Agent 持有不同的上下文窗口，各做各的，避免相互干扰。
4. **人类组织的天然映射**：业务上就是多角色协作（策划 / 设计 / 法务 / 财务）。
5. **可审计 / 可替换**：每个 Agent 都是明确职责的模块，便于替换和评估。

如果上面都不成立，再问自己一遍"我是不是在为拆而拆"。

## 6.3 Multi-Agent 的五种经典拓扑

### 6.3.1 单 Agent + 工具（对照组）

```
         User
          │
          ▼
       [Agent]
          │
      ┌───┴───┐
    Tool A  Tool B
```

**再强调一次**：如果它够用，就用它。

### 6.3.2 Orchestrator–Worker（编排-工人）

```
         User
          │
          ▼
     [Orchestrator]
          │
     ┌────┼────┐
     ▼    ▼    ▼
  [W1]  [W2]  [W3]
```

- 一个主 Agent 理解任务并分派
- 子 Agent 各做各的，结果汇总
- **最稳健、最常用的 Multi-Agent 模式**
- 适合：研究、报告、复杂审批
- Anthropic Claude Code 的 SubAgent、OpenAI Deep Research 都是这种

**PM 关注**：
- Orchestrator 的职责定义得有多清楚？
- Worker 是否会"越权"做不属于自己的事？

### 6.3.3 Pipeline（管道 / 顺序）

```
 User → [A] → [B] → [C] → Output
```

- 每个 Agent 是前一个的"下游"
- 像传统流水线
- 适合：流程稳定的生产线（内容生产、合同审查）
- **注意**：这本质很接近工作流。常常反而用"工作流 + 节点内 Agent"更清晰。

### 6.3.4 Debate / Peer Review（辩论 / 互评）

```
   User
     │
     ▼
  [Agent A] ──提案──▶
                       [Judge]
  [Agent B] ──提案──▶
```

- 多个 Agent 给出不同方案，一个 Judge（可以是 LLM 或人）评选
- 适合：创意、定价、方案评审
- 成本高，但能提升质量上限

### 6.3.5 Swarm / 动态路由

```
        [Router]
           │
     ┌─────┼──────┐
     ▼     ▼      ▼
   [Expert]...[Expert]
     │     │      │
     └──hand off──┘（Agent 之间动态移交）
```

- 动态决定下一步找谁
- 典型实现：OpenAI 的 Swarm / Handoff
- 适合：客服（从通用 → 技术 → 账户 → 退款 专家之间跳转）
- 难点：避免无限 handoff

## 6.4 通信与协作：Agent 之间怎么说话

两种主要方式：

| 方式 | 描述 | 适合 |
|---|---|---|
| **消息传递** | Agent 之间直接聊天（自然语言） | 灵活、类人协作 |
| **共享黑板** | Agent 读写同一块"工作区"（文档/状态） | 长任务、异步、可追溯 |

**一个容易被忽视的 PM 决策**：
- 消息传递：上下文容易爆炸、信息失真
- 共享黑板：需要精心设计"工作区结构"（这其实又回到了记忆/知识库的问题）

实践上，越复杂的系统越倾向于 **共享黑板 + 显式消息**的组合。

---

## 6.5 上下文隔离：Multi-Agent 的核心价值

很多人忽视的一点：Multi-Agent 的**最大实用价值**不是"更聪明"，而是**给每个 Agent 独立的上下文窗口**。

- 如果全部塞一个上下文 → 很快爆掉、注意力分散
- 拆成子 Agent，每个子 Agent 只看**自己任务**所需上下文
- 汇总阶段只接收**子 Agent 的摘要**

这让系统能处理**远大于单 LLM 上下文窗口**的任务（深度研究、整书分析、大仓库重构）。

🧭 PM 视角：当你发现"单 Agent 因为上下文过长开始出错"，这是考虑 Multi-Agent 的**正当信号**。

---

## 6.6 共享状态设计

Multi-Agent 的记忆/状态比单 Agent 复杂一个级别：

| 状态范围 | 举例 | 谁能读写 |
|---|---|---|
| 私有（Private） | A 的思考草稿 | 只有 A |
| 共享（Shared） | 任务目标、进度、核心结论 | 所有相关 Agent |
| 只读（Read-only） | 用户原始需求 | 所有 Agent |
| 外部（External） | 知识库、记忆层 | 有权限者 |

**🛠 建议实践**：一份"任务工作区（Task Workspace）"文档，由 Orchestrator 维护，子 Agent 只能写自己的 section，读取全部。

## 6.7 🧭 Multi-Agent 设计的九个关键决策

PM 在启动 Multi-Agent 设计时，请逐项回答：

1. **角色划分**：拆几个？每个叫什么？职责边界是什么？
2. **拓扑**：Orchestrator-Worker / Pipeline / Debate / Swarm？
3. **路由机制**：谁决定下一步谁来？规则 or LLM？
4. **上下文传递**：什么信息过去？怎么压缩？
5. **共享状态**：是否有工作区？结构如何？
6. **并行 vs 串行**：哪些 Agent 可以并行？
7. **终止条件**：什么情况整个任务结束？
8. **失败重试**：某个 Agent 失败，整体怎么办？
9. **成本上限**：单任务最大成本 / 最大步数？

## 6.8 Multi-Agent 的四大"翻车模式"

### 翻车 1：无限 Handoff
A 说"这个找 B"，B 说"这个找 C"，C 说"找 A" → 死循环。
对策：移交次数上限、强制最终回答。

### 翻车 2：共识幻觉
所有 Agent 一开始参考同一段文档，最后看似达成"一致"，其实全是同一个偏见的回声。
对策：给每个 Agent 不同的资料 / 视角；引入 Judge / 对抗性 Agent。

### 翻车 3：上下文膨胀
Agent 之间每次说话都把"完整历史"丢过去 → token 爆炸。
对策：传递摘要；用共享黑板替代消息传递。

### 翻车 4：错误放大（Error Cascade）
A 的一个小错，传到 B → B 基于错的做决定 → C 更错。
对策：每步做"sanity check"（接 5.4 反思）；关键节点引入人审。

## 6.9 单 Agent vs. Multi-Agent 选型表

| 维度 | 单 Agent | Multi-Agent |
|---|---|---|
| 延迟 | 低 | 高（尤其串行） |
| 成本 | 低 | 高（N 倍） |
| 可预测性 | 中 | 低 |
| 可调试 | 容易 | 困难（trace 爆炸） |
| 质量上限 | 受限于模型 + prompt | 可能更高（分工 + 反思） |
| 适用性 | 绝大多数产品 | 特定场景 |

**👉 默认单 Agent，证据充分再升级 Multi-Agent。**

## 6.10 真实案例：深度研究 Agent（Multi-Agent 的"甜区"）

**目标**：用户给一个开放性问题（"帮我研究某赛道过去 3 年的变化与核心玩家"），产出一份研究报告。

**为什么 Multi-Agent 合适**：
- 需要并行检索多个方向（并行）
- 每个方向的上下文巨大（隔离）
- 最终要综合（Orchestrator 编排）

**拓扑**（Orchestrator–Worker 组合）：

```
                    [Planner/Orchestrator]
                              │
                  拆出 N 个子问题 / 方向
                              │
        ┌────────────┬────────┴────────┬─────────────┐
        ▼            ▼                 ▼             ▼
   [Researcher 1] [Researcher 2]  [Researcher N]  [Source Critic]
   - 搜集资料    - 搜集资料        - 搜集资料     - 评估来源可靠性
        │            │                 │             │
        └────────────┴─────────────────┴─────────────┘
                              │
                         汇总摘要
                              │
                              ▼
                      [Writer Agent]
                              │
                              ▼
                      [Reviewer Agent]
                              │
                              ▼
                           用户
```

**PM 关注点**：
- 每个 Researcher 的资料**不互相串扰**
- Source Critic 是"对抗性 Agent"，防止共识幻觉
- Reviewer 是最后的 Reflection
- 用户能看到完整**执行日志**（信任的关键）

## 6.12 📊 Multi-Agent 的指标

除了单 Agent 的那些指标（模块 01/07），还要加：

| 指标 | 意义 |
|---|---|
| 子 Agent 成功率（分角色统计） | 谁是瓶颈 |
| 子 Agent 间 Handoff 次数 | 过多 → 路由有问题 |
| 平均路径长度 | 拓扑效率 |
| 任务总 token / 总成本 | 是不是多花了冤枉钱 |
| 并行度利用率 | 有没有真的并行 |

## 6.13 团队组织的隐喻：Agent 不是员工

很多人把"多个 Agent"当作"AI 团队"，这个比喻很危险：

- **员工有长期记忆**（培训、经验），Agent 没有
- **员工能自我反思**（沟通），Agent 只能被动反思
- **员工会判断"这事我做不了"**（升级上报），Agent 往往硬着头皮做

所以组织隐喻当"脚手架"可以，当真设计就容易翻车。

**更准确的隐喻**：Multi-Agent = **一个拆成多个进程的并行计算系统**，你要像设计分布式系统一样设计它（超时、重试、幂等、一致性）。
